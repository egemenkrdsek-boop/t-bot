# Local session checkpoints

The previous store silently removed oldest user turns once its JSON exceeded 10 MiB. A single oversized turn could therefore save successfully with no messages. New saves never discard history to satisfy a file limit. This does not recover history already removed by an older release.

`sessions/<session UUID>.json` is now a small `tbot-session-v2` manifest containing session metadata, title, message count and ordered segment descriptors. Each descriptor names an immutable, session-owned `.UUID.generationUUID.index.seg` file with its byte length and SHA-256 checksum. Segments contain UTF-8 newline-delimited message JSON and are at most 1 MiB. A message, including a single message above 10 MiB, may cross any number of segments. UTF-8 decoding preserves code points crossing a boundary.

A save redacts and serializes one message at a time, removes its top-level image attachments as before, writes and syncs all new segments, writes and syncs a temporary manifest, then atomically renames that manifest over the previous checkpoint. Failure before rename leaves the previous checkpoint usable and removes the unfinished generation. Once the manifest is committed, cleanup is best effort and cannot turn a successful save into an error. A crash may leave an orphan generation; the next successful save removes it. A process-wide FIFO queue serializes calls for the same resolved directory/session across store instances, including filesystem lock acquisition. The existing file lock also serializes get/save/delete across processes so a reader cannot lose old segments to cleanup while loading. List reads only manifest metadata and needs no segment lock.

The store synchronously resolves the physical sessions directory (or its nearest existing ancestor plus missing path suffix) during construction. Junction/symlink aliases therefore share the same FIFO key even before the sessions directory exists; Windows queue keys also fold case. This assumes the configured directory is not replaced with a different junction while a store instance is in use.

Every checkpoint has a generation UUID. `createSession` and `get` attach an enumerable symbol revision to the host Session object; object spread preserves it and JSON serialization omits it. Successful save updates the caller's revision. Under the file lock, save compares that expected revision with the current checkpoint before writing anything. Independent stale snapshots fail explicitly with a checkpoint-conflict error instead of overwriting another writer's history, including across processes. Same-object queued appends execute in FIFO order and use the preceding successful revision. To update an existing session, use a Session obtained through `get`, preserve its symbol through normal object spread, and await saves when constructing successive clones. Reconstructing a Session from JSON/IPC loses its revision and must be followed by a host-side `get` before saving; the desktop agent already reloads by session ID on the host. Frozen/nonextensible objects that cannot receive revision updates fail before writing. Legacy checkpoints receive a content-derived revision on `get` and migrate when saved. This is optimistic conflict detection, not an automatic history merge.

Cleanup unlinks only exact generated segment basenames belonging to the validated session UUID. It never traverses manifest-provided directories or recursively removes paths. Reads reject segment traversal, foreign session names, symlinks, invalid lengths, duplicate descriptors, checksum changes, incomplete records and count mismatches. Files retain the existing private creation modes (0700 directory, 0600 files, subject to the host filesystem). Workspace checks remain enforced for get/save/delete. SHA-256 detects accidental corruption; it does not authenticate against a local actor who can rewrite both manifest and segments.

Existing monolithic JSON sessions remain readable and migrate on their next save. Listing such legacy sessions still parses their JSON; newly saved sessions list without parsing history. The new format requires an updated application; older versions cannot read its manifest. The API still returns the complete `Message[]`, so the caller and UI can use their existing contracts.

Loading has an explicit default 256 MiB serialized-transcript budget, configurable through `new SessionStore(dataDir, { maxLoadBytes })`. The manifest is checked before reading transcript segments; exceeding the budget fails with a message that history remains on disk. Manifest reads use their separate 10 MiB cap, so even a transcript budget smaller than the manifest leaves metadata listing and deletion available. Save and delete do not load an existing segmented history. There is no total-history truncation on save; the manifest itself has a 10 MiB limit and saving fails explicitly if it exceeds that limit. Legacy reads also respect the configured byte budget (format discrimination may parse up to the metadata cap).

This is a disk checkpoint solution, not constant-memory replay. Loading retains the full messages array and temporarily holds one JSON message plus segment buffers; a giant individual message therefore needs memory proportional to its size. Save also temporarily serializes one message and rewrites the complete checkpoint, so disk work is linear in history size and old/new checkpoints briefly coexist. Metadata listing is limited to the existing 200 results. Segment and manifest fsync plus atomic rename protect ordinary interrupted writes; no claim is made of transaction durability across every operating system/filesystem or sudden power failure (directory rename durability depends on the host).

Filesystem tests cover a single 11 MiB message, an aggregate transcript above 10 MiB, Unicode segment boundaries, tool linkage, redaction/images, legacy migration, metadata-only listing, explicit load-budget failure with a budget smaller than its manifest, failed segment/manifest writes, concurrent reader/save locking, delayed-lock FIFO order across instances, object-spread revision preservation, stale-snapshot conflicts, workspace/path guards, corruption detection and safe orphan cleanup. No live provider or E2E calls are involved.
